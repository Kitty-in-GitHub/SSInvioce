# 材料上传与程序处理流程（现状）

> 适用版本：当前工作区代码。描述的是"现在实际怎么跑"，不是设计目标。
> 关键实现集中在 `backend/app/routers/{materials,classify}.py`、
> `backend/app/services/{features,cluster,analyze_jobs,amount}.py`。

---

## 1. 总览

材料进入系统有 **四条路径**：

| 入口 | 位置 | 一次上传 | 后端接口 | 落库方式 |
|---|---|---|---|---|
| A. 条目内单文件上传 | 条目详情页槽位「上传/替换」 | 1 个 | `POST /api/materials/upload` | 直接挂到条目，识别异步补写 |
| B. 列表页槽位上传 | 条目列表每行槽位点击 | 1 个 | 同上 | 同上 |
| C. 收件箱「上传」（快速） | 收件箱页 | N 个 | `POST /api/materials/upload-batch` | 只落盘进收件箱，不识别 |
| D. 「整理」弹窗 | 收件箱 / 条目页的「整理」按钮 | — | `/api/classify/recluster` → `/confirm` | 只整理收件箱已有材料，**不再提供上传入口** |

**收件箱 = `materials.entry_id IS NULL`**。快速上传的文件只写库（`analyze_status='raw'`），
关窗口、刷新、重启后端都不会丢；「整理」弹窗是收件箱的批量视图，只做识别、聚类和归档。

```
单文件 ─▶ /api/materials/upload ─▶ 挂到条目 + 后台识别
多文件 ─▶ /api/materials/upload-batch ─▶ 收件箱材料(type=unknown, status=raw)
                                              │
                       /api/classify/recluster（整理时才惰性抽特征）
                                              ▼
                       /api/classify/confirm ─▶ 新建条目 / 并入已有条目
```

## 2. 通道 A / B：单文件上传

### 2.1 前端交互

- 详情页：每个槽位一个隐藏 `<input type="file">`，`accept` 由槽位 `file_kind` 决定。
  选中后立刻用 `URL.createObjectURL(file)` 本地预览，按钮进入「处理中…」。
- 列表页：点击空槽位 → 选文件 → 立即上传。
- 成功后：`load({ silent: true })` 刷新条目 → `kickAnalyzePolling()` 触发
  `/api/materials/jobs` 轮询 → 提示「已上传，正在后台识别」。
- 详情页在存在 `processing=true` 的材料时每 1.6s 轮询一次，直到没有 pending。
- 全局 `AnalyzePendingGuard` 在还有 pending 时悬浮提示，并在关闭/刷新时弹确认。

### 2.2 后端 `POST /api/materials/upload`

`backend/app/routers/materials.py:49`

1. **校验**：文件名必填；扩展名必须在
   `{.pdf,.jpg,.jpeg,.png,.webp,.bmp,.gif}` 内，否则 400。
2. **条目校验**：带 `entry_id` 时确认条目存在，否则 404。
3. **读入内存**：`await file.read()`，空文件 400（整份文件进内存）。
4. **落盘**：`store_upload()` → `data/uploads/<entry_id>/<uuid4hex>_<安全化文件名>`；
   没挂条目时目录是 `data/uploads/inbox/`。返回相对路径存库。
5. **取尺寸**：非 PDF 用 PIL 读宽高；PDF 宽高留空。
6. **定类型**：显式 `type`（前端槽位已知）优先；否则 `classify_file()`：
   `.pdf` 一律发票槽；图片只在图片类槽位关键词里匹配文件名，命中即该槽，否则 `unknown`。
7. **元数据**：mime 猜测、`sha256` 内容摘要。
8. **入库（单事务）**：
   - `INSERT materials(..., analyze_status='pending')`；
   - 若挂了条目：删除**同条目同类型**旧材料行（**替换语义**），旧文件异步删；
   - 更新 `entries.updated_at`；
   - 金额先做一次"文件名兜底"（`read_pdf=False`）。
9. **返回** `MaterialOut`，`processing = (analyze_status == 'pending')`。
10. **排队识别**：`submit_analyze(material_id)`，1 个 worker 的线程池。

### 2.3 后台识别 `_run`

`backend/app/services/analyze_jobs.py:98`

1. 重查材料（可能已删 → 跳过）。
2. `extract_features()`：
   - **文本**：PDF 用 PyMuPDF 取**前 2 页**；图片走 RapidOCR；扫描版 PDF 不 OCR。
   - **金额**：文件名优先，其次文本（`实付价`/`实付款` > 微信账单 `-30.09` >
     `价税合计/合计` > `￥数字`，跳过"共减/立减"）。
   - **类型**：按后缀筛同 `file_kind` 槽位，关键词正文命中 +2、文件名 +1，取最高分；
     无命中时 PDF→发票槽，图片→`classify_file()`→可能 `unknown`。
   - **字段**：商家、商品名、日期、订单号、发票号码/代码（全角转半角）、内容 sha256。
3. **回写**：`invoice_number`/`invoice_code`（仅发票槽）、`content_sha256`、
   `analyze_status='done'`。
4. **挂条目时**：`apply_auto_amount()`，`amount_source='manual'` 不覆盖。
5. **查重**：发票号码查已挂条目材料，只写日志，不阻断。
6. **异常**：`analyze_status='error'`；退出时等待线程池，启动时恢复 `pending`。

## 3. 收件箱整理（不含上传）

### 3.1 前端交互（`BatchUploadPanel.vue`）

1. 从收件箱或条目页点「整理」打开；打开时 `POST /api/classify/recluster`
   （`temp_ids: null` = 全部收件箱）载入已有材料。
2. 渲染三块：
   - **拟建条目**：标题、金额、每个必填槽位一张卡片（可预览、可改类型），
     以及「归属」下拉：新建条目 / 并入某个未齐套条目（只补缺失槽位）；
   - **未匹配**：文件名、文本预览、金额、类型下拉，以及归属选择
     （放收件箱 / 挂到条目 / 新建条目 / 并入某个拟建条目）；
   - **重复副本**：同批里内容相同的文件被自动折叠，只留一个代表参与聚类；
     可勾选"入库时把重复副本移入回收站"（默认勾选，可取消）。
3. 改类型会立即 `PATCH /api/materials/{id}` 持久化，关窗再开不会丢。
4. 每个簇右上角有垃圾桶图标（丢弃本簇），每个已填槽位有「×」：都是**移入回收站**（可恢复），
   不会删除已入库条目。
5. 顶部是**固定工具条**（标题、计数、操作、关闭都在这里，不随内容滚动），下方只有内容区滚动：
   左侧是标题和「拟建 / 未匹配 / 重复副本」计数 + 次要的「重新归组」；右侧是「丢弃重复（N）」、
   主操作「确认入库」和最右的红色 **×** 关闭按钮。
   「丢弃重复」一次性丢弃所有带重复警告的簇 + 折叠出的重复副本（都进回收站）。
6. **弹窗内没有上传入口**；收件箱为空时只显示提示。**关闭窗口不删除任何材料**。

### 3.2 后端 `POST /api/classify/preview`（旧入口，UI 已不使用）

> 早期"批量上传 + 即时聚类"接口，当前界面的「整理」不再调用；保留用于脚本或兼容。

`backend/app/routers/classify.py:271`

1. 逐文件：扩展名校验 → 读内容 → `store_upload(entry_id=None)`（落 `inbox/`）
   → 图片取宽高 → `extract_features()` → **直接 INSERT materials**
   （`entry_id=NULL`、`analyze_status='staged'`、`features_json` 缓存特征、
   发票槽才写发票号/代码）。
2. `_build_preview_payload()` 先做**同批去重折叠**（`_fold_duplicates`）：
   发票按发票号码分组、其它文件按 `内容 hash + 类型` 分组；每组保留一个代表，
   其余标记 `duplicate_of` 并**排除在聚类之外**（响应里的 `duplicate_temp_ids`）。
   然后读取**当前全部收件箱材料**重新聚类并返回快照（多次拖拽是累积的）。
3. **聚类算法**（`services/cluster.py:205`）：
   - 按金额（两位小数）分桶；无金额单独一堆；
   - 同金额组内文件数 > 3 时按 `商家|日期|订单号` 再拆；
   - `_pack_trio`：按设置里的**必填槽位**（默认 invoice/order/payment）贪心各取一份成簇；
   - 余料用 `_try_attach` 补进不完整簇：金额相同 +5、簇金额为空 +1、商家前 12 字相同 +4、
     订单号相同 +6、日期相同 +2；唯一候选兜底 +1；
   - 仍剩下的再 `_pack_trio` 一次；
   - 标题 = `商品名 or 商家 or 发票文件名` + 日期 + `¥金额`。
4. **查重**（每个簇，簇内**所有**材料都参与）：
   - 发票号码（仅发票）→ 已挂条目的发票（`invoice_number`）；
   - 文件哈希（任意类型：发票 / 订单 / 支付）→ 已挂条目的材料（`existing_file_hash`）；
   - 发票号码（仅发票）→ 收件箱里**另一个**未整理发票（`same_batch_number`）；
   - 文件哈希（任意类型）→ 收件箱里另一个文件（`file_hash`）。
   命中后带 `existing_type`，前端显示如“与已有条目「周转箱 17.61」里的订单截图是同一份文件”。
5. 返回：`items`（含 `duplicate_of`）、`clusters`、`unmatched_temp_ids`、
   `duplicate_temp_ids`、`ocr_available`。

> `temp_id` 就是**材料 id 的字符串形式**（沿用旧字段名，前端当不透明 key 用）。

### 3.3 重新聚类 `POST /api/classify/recluster`

`backend/app/routers/classify.py:405`

- 从 `materials WHERE entry_id IS NULL` 读取（可传 `temp_ids` 限定子集）；
- 有 `features_json` 直接用；没有的（老收件箱材料）现场抽一次并写回缓存；
- 材料当前 `type` 优先于 `features_json` 里的 `suggested_type`（尊重手工改类型）。

### 3.4 确认入库 `POST /api/classify/confirm`

`backend/app/routers/classify.py:431`

1. **按簇**：校验材料存在、`entry_id` 为空、类型非 `unknown`；发票查重（结果进 `warnings`，不阻断）。
   - `entry_id` 为空 → `INSERT entries(...)` 新建条目，材料挂上去，并尝试自动金额；
   - `entry_id` 有值 → **并入已有条目**（补传）：不新建条目，先检查目标条目是否已有同槽材料，
     有冲突就 400 并提示先删旧材料；成功则只 `UPDATE` 材料，**不覆盖条目已有金额**
     （仅当条目金额为空、且不是手改时，用簇金额补齐），并 `sync_entry_ledger`。
2. **按散件**：`entry_id` 有值 → 挂已有条目；`create_entry_title` → 新建条目；
   都没有 → 保持 `entry_id=NULL`，留在收件箱。
3. **不插入新材料行**，只改现有行；已挂条目的材料再次确认会返回 400。
4. 返回 `{ok, created_entry_ids, updated_entry_ids, material_ids, warnings}`。
   前端确认成功后，若勾选了"丢弃重复副本"，会再调一次 `/api/classify/discard`
   把 `duplicate_temp_ids` 移入回收站。

> 前端簇卡片有一个「归属」下拉：默认"新建条目"，其余只列出
> **缺该簇某个槽位、且没有同槽冲突**的未齐套条目；选中后标题输入禁用，金额仅在目标条目为空时生效。

### 3.5 丢弃 `POST /api/classify/discard`

`backend/app/routers/classify.py:358`

- 只允许丢弃 `entry_id IS NULL` 的材料（已挂条目的会 400）；
- 文件移到 `data/trash/`、写入 `trash` 表（`reason='classify_discard'`，同一批共用一个 `batch_id`）；
- 删除 `materials` 行，返回丢弃后的收件箱快照。

### 3.6 回收站 `/api/trash`

| 接口 | 作用 |
|---|---|
| `GET /api/trash` | 按删除批次分组列出（文件名、类型、大小、原条目、删除时间） |
| `POST /api/trash/restore` `{ids}` | 恢复：原条目还在且该槽位空闲 → 回原条目；否则回收到收件箱 |
| `POST /api/trash/purge` `{ids}` | 彻底删除（删文件 + 删记录） |
| `DELETE /api/trash` | 清空回收站 |
| `DELETE /api/trash/{id}` | 彻底删除单条 |

- 进入回收站的路径：整理丢弃、收件箱/条目里删除材料、删除整个条目（`reason='entry_deleted'`，
  原条目已不存在，恢复时回到收件箱）。
- 启动时清理超过 **30 天** 的记录与文件（`services/trash.py::cleanup`）。
- **上传替换**（同槽位上传新文件）仍直接删旧文件，不进回收站。

### 3.7 快速上传（收件箱）`POST /api/materials/upload-batch`

- 收件箱页「上传」按钮，可多选；只做落盘 + 写 `materials`：
  `type='unknown'`、`analyze_status='raw'`、记录 sha256 与尺寸；
- **不跑 OCR / 分类 / 金额，也不排分析任务**，所以上传反馈快；
- 首次打开「整理」时，`_feature_for_row()` 才抽特征，把识别到的类型回写（`raw → done`）；
- 未整理前在收件箱里显示「待识别」，也可以手动改类型或挂到条目。

## 4. 落盘与数据模型

```
data/uploads/
  <entry_id>/<uuid>_<安全文件名>    # 已挂条目的材料
  inbox/<uuid>_<安全文件名>         # 收件箱材料（快速上传 / 先放收件箱）
data/app.db                        # SQLite
```

`materials` 关键列：`entry_id, type, original_name, stored_path, mime, width, height,
created_at, invoice_number, invoice_code, content_sha256, analyze_status, features_json`。

- `features_json`：`FileFeatures` 的 JSON 缓存（金额/商家/日期/订单号/发票号/哈希等），
  让收件箱材料在重启后无需重跑 OCR 即可重新聚类。
- `stored_path` 是相对 `data/uploads/` 的路径，读取时 `resolve_stored()` 做越界校验。
- `entries` 金额三列：`amount`、`amount_source ∈ {auto, manual, empty}`、`amount_auto`。
- **齐套**由 `required_slot_ids()` 与材料类型集合实时比较得出（不落库）。

## 5. 状态机与生命周期

| 对象 | 状态 | 迁移 |
|---|---|---|
| 材料 `analyze_status` | `pending` | 单文件上传后置位；后台识别完成 → `done`；异常 → `error`；重启重新排队 |
| | `staged` | 旧版批量预览写入收件箱（当前 UI 不再使用）；确认入库后 → `done`；丢弃则移入回收站 |
| | `raw` | 收件箱「上传」快速入库（不识别）；首次整理时抽特征并 → `done` |
| | `done` | 识别完成 / 已入库 / 确认时选择"先放收件箱" |
| 金额来源 | `empty → auto → manual` | 自动识别写 `auto`；手改写 `manual` 后自动逻辑不再覆盖；可强制重识别 |
| 收件箱材料 | `entry_id IS NULL` | 确认入库或手动挂条目后 `entry_id` 有值；删除则移入回收站 |
| 回收站记录 | `trash` 表 | 30 天后自动清理；恢复后重新插入 `materials`（新 id） |

> 旧版本用进程内 `_STAGING` 字典暂存，现已移除：暂存态就是数据库里的收件箱材料。

## 6. 现状要点 / 需要注意的地方

1. **单文件上传是"替换"语义**：同条目同类型旧材料会被删除（文件异步删）。
2. **并入已有条目不会替换**：簇的「归属」选已有条目时，目标条目已有的同槽材料会让确认直接 400
   （提示先删旧材料），不会产生同槽两份；但**散件**选"挂到已有条目"仍不检查冲突，
   拼版时 `materials_by_slot()` 取 `id` 最小的那份。
3. **批量 preview 同步跑 OCR**：`/api/classify/preview` 是 `async def`，却在事件循环里
   直接调用同步的 `extract_features()`，文件多/图大时会阻塞其它请求。
   单文件链路的识别并发度为 1（单 worker 线程池）。
4. **PDF 只读前 2 页文本，且不做 OCR**；扫描版 PDF 的金额只能靠文件名兜底。
5. **新版电子发票的号码提取**：这类 PDF 把标签和值放在不同文本块，号码与开票日期在提取文本里
   粘成 `<20位号码><YYYY>年<MM>月<DD>日`；`features._extract_invoice_number()` 已加专门回退。
6. **查重只提示不阻断**：preview 有警告，`confirm` 返回的 `warnings` 前端目前未使用。
7. **收件箱会累积**：上传后不整理就一直留在收件箱；「整理」会把它们全部纳入聚类。
8. **旧版遗留的孤儿文件**：老 `_STAGING` 时代可能留下 `inbox/` 里没有数据库行的文件，
   新版本不会自动认领，也不会自动删除（可按需手工清理）。
9. **文件只校验扩展名**，不校验 MIME/大小；按本机单用户场景设计。
10. **手改金额受保护**：`amount_source=manual` 时自动识别不覆盖，需显式 `force` 重识别。
11. **查重范围**：按文件内容（`content_sha256`）对**所有类型**生效，所以重复上传同一张订单/支付截图
    也会提示；发票号码只在发票之间比较。历史发票可能没有号码（旧版本提取失败），
    这类只能靠文件哈希命中；重新下载导致字节不同的同一张发票目前抓不到。
12. **回收站**：显式删除（批量丢弃、删材料、删条目）都会移入 `data/trash/` 并在 `trash` 表留记录，
    保留 30 天；「上传替换」仍直接删除旧文件，不进回收站。
    恢复时原条目还在且槽位空闲 → 回原条目，否则回收到收件箱（`materials` 重新插入、id 会变）。
13. **同批重复折叠**：同一批里发票号相同（即使字节不同）或内容 hash+类型相同的文件，
    只保留一个代表参与聚类，其余列为"重复副本"；确认入库时按勾选批量移入回收站。
14. **重新归组**：按材料当前类型重新聚类，会重建簇（未保存的簇标题 / 金额 / 并入选择会丢）。
    只在"改了材料类型、需要把它换到别的簇"时用；上传、丢弃、重新打开弹窗都会自动重聚类。
